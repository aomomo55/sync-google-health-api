# UI・UX 観点のレビュー

通知・画面・ノート・エラー文を、利用者の側から見て確かめるための材料。前半（流れと確認項目）は「何が伝わるか」、後半の「画面の見た目と操作（UI）」は「どう見えて、どう操作できるか」を扱う。コードの差分を見る観点は [REVIEW.md](../../REVIEW.md) にあり、ここはそこから参照する。置き場所を決めた理由は [ADR 0024](../adr/0024-ux-review-in-docs-review.md)。

ここには「何を確かめるか」と「どこを見るか」だけを書く。今のコードがどう動いているか、どこに問題があるかは書かない（直すと古くなるため）。見つかった問題は Issue にする。

## いつ使うか

- 通知・画面の表示や配置・送信結果の文・エラー文・ノートの構成を変える PR。REVIEW.md の「利用者の体験（UX）」の節から、下の確認項目のうち関係するものを見る
- ときどき（大きな機能を足したあとなど）、下の 2 つの流れを最初から最後までたどり直す

## 利用者の前提

- 利用者はほぼ本人 1 人。設定や仕組みは分かっているが、毎朝は寝起きで、時間をかけずに判断したい
- 毎日目にするのは、アプリの画面よりも **通知と Obsidian のノート**。アプリを開くのは、何かおかしいと気づいたときか、設定を変えるとき
- そのため、問題は「アプリを開けば分かる」では足りず、通知かノートで気づけるかを重く見る

## 毎朝の流れ

| 段階 | 利用者がしたいこと | 確かめること | 見るところ |
|---|---|---|---|
| 1. 起床前 | 何もしない（自動送信に任せる） | 起床前に通知が鳴らないか。自動送信が止まっていても、後の段階で気づけるか | `android/.../SyncWorker.kt`、`SyncRunner.kt`、`MissingSleepCheck.kt`、`SyncFailureCheck.kt` |
| 2. 起床後の通知 | 昨夜の睡眠が届いたかを知る | 通知が出る条件と出ない条件。出ないことが「届いている」を意味するか。通知の文だけで次の行動が分かるか。タップした先で行動できるか | `MissingSleepCheck.kt`、`MissingSleepNotifier.kt`、ADR 0022 |
| 3. ノートを開く | 昨夜の睡眠と前日の活動を見る | 判断に要る情報が最初に目に入るか。データが無い項目について、「まだ届いていない」「記録が無い」「0」の区別がつくか | `server/src/notes/daily.ts`、`monthly.ts` |
| 4. 判断する | その日の過ごし方を決める | 古いデータや欠けたデータのまま判断が進んでしまわないか。届いていないときに、取り込み直す方法がすぐ分かるか | 上の 2・3 |

## 壊れたときの流れ

それぞれの壊れ方について、**いつ・どこで・どう気づけるか**と、**気づいたあと何をすればよいかが分かるか**を確かめる。

| 壊れ方 | 確かめること | 見るところ |
|---|---|---|
| トークンが違う・消えた | 自動送信が失敗し続けたとき、通知かノートで気づけるか。エラー文に、どこで何を直すかが書いてあるか | `SyncRunner.kt`、`SyncFailureCheck.kt`、`IngestClient.kt`、`docs/rotate-secrets.md` |
| Health Connect の権限が外れた | どの権限が足りないかが分かるか。一部の権限（栄養など）だけ足りないときの扱いが分かるか | `SyncRunner.kt`、`PermissionPolicy`、`MainActivity.kt` |
| 通知の権限が無い・拒否済み | 通知が出ないことに気づけるか。OS がダイアログを出さなくなったあとの手段が示されるか | `MissingSleepNotifier.kt`、`MainActivity.kt` |
| サーバーが落ちている・5xx | 自動で再試行されることが分かるか。落ち続けたときに気づけるか | `IngestClient.kt`、`SyncWorker.kt`、`SyncFailureCheck.kt` |
| ネットワークにつながらない | 自動送信が静かに止まったときに気づけるか | `SyncWorker.kt` の実行条件 |
| データは保存できたが、ノートの書き込みに失敗した | 送信が成功扱いになったときに、ノートが古いことに気づけるか。どのノートが、次に何をすれば直るかが分かるか | `server/src/routes/health.ts`、`server/src/sync/note-sync.ts`、`SyncMessage.kt` |
| 範囲外の値の日が保存されなかった | 長い結果の文に埋もれずに気づけるか | `server/src/routes/health.ts`、`SyncMessage.kt` |
| 応答が遅い（自動停止からの起動、ノートの書き込みのやり直し） | 保存できているのに失敗に見えることがないか | `IngestClient.kt` のタイムアウト、`server/src/vault/` のやり直し |

## 確認項目

### 状態が分かるか

- [ ] 画面の「最終送信」などの時刻が、成功した時刻なのか試した時刻なのかが分かるか
- [ ] 自動送信が動いているか（止まっていないか）を、アプリを開かずに知る手段があるか

### 問題に気づけるか

- [ ] 送信の失敗が続いたとき、通知かノートで気づけるか（アプリを開くまで分からない作りになっていないか）
- [ ] 通知が「出ない」ことが、正常と異常のどちらの意味にも取れてしまわないか
- [ ] ノートでデータが無い項目について、「まだ届いていない」「記録が無い」「0」の区別がつくか。日によって表し方が変わらないか
- [ ] 一部だけ失敗した（保存はできたがノートは書けなかった、範囲外の日があった）ときに、成功の扱いに埋もれていないか

### エラーから立ち直れるか

- [ ] エラー文に、何が起きたかと、次に何をすればよいか（どの画面で何を直すか、待てば直るのか）が書いてあるか
- [ ] 「サーバーのログを確認してください」で終わらず、本人が取れる行動が示されているか

### 迷わずに使えるか

- [ ] 送り方が複数あるとき、どれを使えばよいかが画面で分かるか
- [ ] 「保存した」と「送った」が混ざらずに分かるか
- [ ] 設定の値（通知の時間帯など）が、なぜその値にするべきかが画面で分かるか

### 言葉の分かりやすさ

- [ ] 「未付与または不足」のようなまとめた表現が、何を指すかが分かるか
- [ ] 同じものを指す言葉（ヘルスコネクト / Health Connect、ウェアラブルのアプリ、など）がそろっているか
- [ ] 特定のメーカーのアプリ名を書かない約束（ルートの AGENTS.md）を守りつつ、何をすればよいかが伝わるか

### うるささ

- [ ] 通知の頻度・時刻・音が、寝ている間に起こさず、起きたあとには気づける程度か
- [ ] 用が済んだ通知（睡眠が届いた、など）が残り続けないか

### ノートの読みやすさ

- [ ] 朝の判断に要る情報が、本文の最初のほうにまとまっているか
- [ ] frontmatter の空の項目が、本文の読みやすさを損なっていないか（frontmatter は Dataview・Bases 向け）
- [ ] 月次ノートで、データが欠けた日があることに気づけるか

### アクセシビリティ

利用者が 1 人なので優先度は低い。

- [ ] 色だけで状態を表していないか（文言も添えているか）
- [ ] 大事な情報を小さい文字（補足用の書式）だけで出していないか

## 画面の見た目と操作（UI）

### Android の画面

操作したあとの手応え

- [ ] ボタンを押したあと、何が起きたかがすぐ分かるか（保存したら、入力欄からフォーカスを外してキーボードを閉じ、保存したことを近くに示す、など）
- [ ] 送信中は、ボタンが押せなくなり、進んでいることが見えるか（何も起きていないように見えないか）
- [ ] 結果やエラーの文が、押したボタンから離れた場所や、スクロールしないと見えない場所に出ていないか。長い文で配置が崩れないか

状態に合わせた出し分け

- [ ] 権限など、足りないと動かない状態が、足りないときに目立つ位置と見た目で出るか（補足用の小さい文字に埋もれていないか）
- [ ] 今の状態では要らない操作（権限がそろっているときの権限のボタン、など）を出したままにしていないか。出し分けたとき、あとで設定を見直す手段は残っているか

配置と部品

- [ ] よく使う操作（今すぐ送信）ほど上にあり、たまにしか使わない操作（設定、過去の日の送信）と見分けがつくか
- [ ] ボタンの種類（塗りつぶしの `Button` / 枠だけの `OutlinedButton` / `TextButton`）が、操作の重要度に合っているか
- [ ] 似たボタンが並んで、押し間違えやすくなっていないか。時間のかかる操作（長い期間の送信）を誤って押しにくいか
- [ ] 入力欄のキーボードの種類（URL、数字）が合っているか。トークンが画面にそのまま見えないか。入力の誤りがその場で分かるか

見え方

- [ ] 端末の文字サイズを最大にしたとき、小さい画面、ダークモードで、文字が切れたり読めなくなったりしないか
- [ ] 色は `MaterialTheme.colorScheme` から取り、直書きしていないか（ダークモードで読めなくなるため）
- [ ] 押せる部品の大きさが 48dp 四方を下回らないか

### 通知の見た目

- [ ] 折りたたんだ状態（タイトルと 1 行目）だけで要点が分かるか
- [ ] ロック画面に、健康データの中身が出ないか
- [ ] タップした先が、通知の内容に合った画面か

### ノートの見た目（スマホの Obsidian）

- [ ] スマホの幅で、表が横にはみ出しすぎないか（列の数、1 列の文字数）
- [ ] 閲覧モードとライブプレビューの両方で崩れないか
- [ ] 見出しの階層と順番で、読みたいところへすぐ移れるか
- [ ] Dataview・Bases の部分が、データが無いときに壊れた表示（エラーや空の表）にならないか

### 確かめ方

- 画面は、エミュレータか実機で、上の条件（文字サイズ最大、ダークモード）に切り替えて見る。権限がそろっているときと足りないときの両方を見る。ノートはスマホの Obsidian で見る
- 見た目を変える PR には、変えた前後のスクリーンショットを添える。ただしこのリポジトリは公開なので、**サーバー URL（本番のホスト名）・トークン・実在の健康データの値が写らないように** する（架空の値を入れた画面で撮るか、隠してから貼る）

## 文言の探し方

Android の利用者向けの文言（画面・通知・エラー）は `android/app/src/main/res/values/strings.xml` にある。機能ごとの接頭辞（`settings_`、`permission_`、`sync_`、`notification_` など）でそろえている。サーバーの文言はコードに直書きされている。一覧はここに写さず、必要なときに探す。

```sh
# Android の利用者向けの文言
cat android/app/src/main/res/values/strings.xml
# コードに文言が直書きされていないか（ログ・例外のメッセージを除く）
git grep -n '"[^"]*[ぁ-んァ-ヶ一-龠][^"]*"' -- 'android/app/src/main/**/*.kt'
# サーバーが返すエラー文とノートの文
git grep -n -E 'error:|message:' -- 'server/src/routes/*.ts' 'server/src/sync/*.ts'
git grep -n -E "[\`'\"]- " -- 'server/src/notes/*.ts'
```

レビューで実例を見るときは、自分の Vault のノートを見てよい。ただし、Issue や PR に実際の健康データの値を書かない（ルートの AGENTS.md）。例を示すときは架空の値にする。
