# 秘密情報が漏れたときの手順

トークンやパスワード、バックアップの秘密鍵が漏れた（漏れたかもしれない）ときに、値を入れ替えて影響を調べる手順。秘密情報の登録の基本は [deploy.md](deploy.md#秘密情報を登録する)、バックアップの鍵は [backup.md](backup.md) にある。

置き換える値は `<…>` で書いている。`<` `>` も含めて自分の値に置き換える。

## 共通の流れ

1. 新しい値を作る
2. サーバー（fly.io の secrets）と、その値を使う側をすべて新しい値にする
3. 古い値が使えなくなったことを確かめる
4. 漏れていた間に何をされた可能性があるかを調べる

漏れた範囲が分からないときは、全部を入れ替える。

### 新しいトークンを作る

64 文字の英数字が出る。`API_TOKEN` と `BACKUP_TOKEN` は別々に作る（同じ値ではサーバーが起動しない）。

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

### サーバーに登録する

値がシェルの履歴に残らないよう、標準入力から渡す。

```sh
fly secrets import -a <アプリ名>
```

1. `KEY=` と打ってから、値だけを貼る。これを 1 行に 1 つずつ入力する（例: `API_TOKEN=` と打ち、続けて新しいトークンを貼って Enter）
2. 最後に Enter で空の行に移ってから、Ctrl-D で終える（終わらなければもう一度 Ctrl-D）

`fly secrets set KEY=value -a <アプリ名>` でも登録できるが、値がシェルの履歴に残る。

### 古い値が使えなくなる時点

サーバーは起動時に secrets を読み、そのときの値だけを受け付ける。secrets を変えるとサーバーは自動で再起動するので、再起動の後は古い値が使えない。再起動したかは `fly logs -a <アプリ名> --no-tail` の `listening on` の行で分かる。

`OBSIDIAN_MCP_TOKEN` と CouchDB のパスワードは、相手側（obsidian-sync-mcp・CouchDB）で値を変えた時点で古い値が使えなくなる。サーバーの secrets を変えるだけでは無効にならない。

### 調べられること・調べられないこと

- サーバーはリクエストごとのログを出さない。誰がいつ呼んだかは記録されていない
- `fly logs -a <アプリ名> --no-tail` で見られるのは、起動・停止とエラーのログで、保存される期間も短い。マシンは使われていないと止まり、リクエストが来ると起動するので、心当たりの無い時刻の起動は手がかりになる
- `health` DB の日次の文書には、最後に書き込んだ時刻 `updated_at`（UTC）がある（[CouchDB の文書を確かめる](#couchdb-の文書を確かめる)）

## 秘密情報ごとの手順

### API_TOKEN

**漏れている間にできること**: `/api/*` のすべて。全期間の健康データの読み取り（`GET /api/summary` など）、日次データの上書きと削除（`POST /api/ingest` で `null` を送ると値が消える）、ノートの同期（`POST /api/notes/sync`）。同期によって、Vault の `VAULT_HEALTH_PREFIX` の下のノートが、書き換えられたデータで作り直される。`/backup/*` は使えない。

**入れ替え**:

1. 新しいトークンを作り、`API_TOKEN=` としてサーバーに登録する
2. Android アプリでトークンを入力し直し、「設定を保存」を押す。入れ替えるまでの自動送信は 401 で失敗する（データは次の送信で送られる）
3. `import:takeout --post` や `sync:notes` で環境変数 `API_TOKEN` に入れている場合や、パスワードマネージャー・`server/dev.vars` に控えている場合は、それも新しい値にする

**確かめること**: 古いトークンで `GET /api/ping` が 401 になること。

```sh
read -rs T
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $T" https://<アプリ名>.fly.dev/api/ping
unset T
```

**影響を調べる**: 漏れていた間に更新された日次の文書を探す（[CouchDB の文書を確かめる](#couchdb-の文書を確かめる)）。書き換えられていたら、Android アプリの「開始日を指定して送る」や Takeout の取り込みで送り直すか、[バックアップから復元](backup.md#復元)する。データを直したら `sync:notes` でノートを作り直す（日次ノートのメモ欄は作り直しても残るので、自分で確かめる）。

### BACKUP_TOKEN

**漏れている間にできること**: `GET /backup/health` で、全期間の日次データのバックアップを取ること。バックアップは age で暗号化されているので、秘密鍵が無ければ中身は読めない。書き込みや `/api/*` は使えない。秘密鍵も漏れている場合は、全データを読める。

**入れ替え**:

1. 新しいトークンを作り、`BACKUP_TOKEN=` としてサーバーに登録する（`API_TOKEN` とは別の値）
2. GAS の「プロジェクトの設定」→「スクリプト プロパティ」の `BACKUP_TOKEN` を同じ値にする
3. GAS のエディタで `runBackup` を実行し、成功することを確かめる

**確かめること**: 古いトークンで `/backup/health` が 401 になること（上の `/api/ping` の例の URL を `https://<アプリ名>.fly.dev/backup/health` にする）。

### OBSIDIAN_MCP_TOKEN

**漏れている間にできること**: obsidian-sync-mcp を直接呼ぶこと。obsidian-sync-mcp が読める範囲のノートの読み取りと、書き込みを許可したフォルダの中でのノートの書き込み・削除ができる。どこまで読めて書けるかは obsidian-sync-mcp 側の設定による（[ADR 0007](adr/0007-write-via-obsidian-sync-mcp.md)）。このサーバーの API や `health` DB には触れない。

**入れ替え**:

1. 新しいトークンを作る（obsidian-sync-mcp が受け付ける形式で、16 文字以上）
2. obsidian-sync-mcp 側の Bearer トークンを新しい値に変える。方法は obsidian-sync-mcp の説明に従う。この時点で古い値は使えなくなる
3. `OBSIDIAN_MCP_TOKEN=` としてサーバーに登録する。2 と 3 の間に届いたデータは保存されるが、ノートの同期は失敗する。登録した後に `sync:notes` でその期間を同期し直す
4. ほかにこのトークンで obsidian-sync-mcp を呼んでいるものがあれば、それも新しい値にする

**影響を調べる**: 書き込みを許可したフォルダのノートに、心当たりの無い変更や削除が無いかを確かめる。サーバーが作るノートは `sync:notes` で作り直せるが、日次ノートのメモ欄とほかのノートは自分で確かめる。

### COUCHDB_PASSWORD

**漏れている間にできること**: CouchDB に直接つなぐこと。`COUCHDB_USER` の権限の範囲で、`health` DB の読み取り・書き換え・削除ができる。CouchDB は Obsidian の同期にも使っているので（[ADR 0005](adr/0005-store-health-data-in-couchdb.md)）、そのユーザーが LiveSync のデータベースにも権限を持っていれば、そちらも消したり壊したりできる（中身は LiveSync の E2EE で暗号化されていれば読めない）。管理者のユーザーなら、ほかのユーザーや設定も変えられる。

**入れ替え**:

1. 新しいパスワードを作る（上のトークンの作り方でよい）
2. CouchDB 側で `COUCHDB_USER` のパスワードを変える。方法は CouchDB の管理画面や、CouchDB を動かしている環境の設定に従う。この時点で古い値は使えなくなる
3. `COUCHDB_PASSWORD=` としてサーバーに登録する。2 と 3 の間は、データの受信が失敗する（Android アプリの自動送信は間隔をあけてやり直す）
4. 同じユーザーを LiveSync や obsidian-sync-mcp、手元の復元（`restore:backup`）でも使っていれば、それも新しいパスワードにする

**影響を調べる**: `health` DB の文書を確かめる（下の節）。消されたり壊されたりしていれば、[バックアップから復元](backup.md#復元)する。LiveSync のデータベースに権限があった場合は、Obsidian の Vault も確かめる。CouchDB 側にアクセスのログがあれば、それも見る。

### age の秘密鍵（バックアップの復号用）

**漏れている間にできること**: その鍵で暗号化したバックアップのファイルを手に入れた人が、中身（全期間の日次データ）を読むこと。鍵だけでは何も読めないが、Google Drive のバックアップや、`BACKUP_TOKEN` で取ったバックアップと組み合わせると読める。サーバーへの書き込みはできない。

**入れ替え**:

1. 新しい鍵の組を作り、保管する（[backup.md の「1. 鍵の組を作る」](backup.md#1-鍵の組を作る手元で)）
2. 新しい公開鍵を `BACKUP_AGE_RECIPIENT=` としてサーバーに登録する（`age1` も含めて 62 文字）。以後のバックアップは新しい鍵で暗号化される
3. GAS のエディタで `runBackup` を実行し、新しい鍵で復号できることを確かめる（[backup.md の「1. 中身を確かめる」](backup.md#1-中身を確かめる書き込まない)）

**古いバックアップの扱い**: 鍵を入れ替えても、Google Drive にある古いバックアップは古い鍵で暗号化されたままで、漏れた鍵で読める。新しい鍵でのバックアップと復号を確かめたら、古い鍵で暗号化したファイル（入れ替える前の日付のもの）を Google Drive から削除し、ごみ箱も空にする。そのうえで古い鍵を保管場所から消す。

- 古いファイルを残しておきたい（過去の時点のデータに戻したい）場合は、それが漏れた鍵で読めることを受け入れて残す。GAS は日次 7 世代・週次 5 世代を残して古いものから消すので、残しても 1 か月ほどで入れ替わる
- 秘密鍵と一緒に Google Drive や `BACKUP_TOKEN` も漏れた可能性があるなら、古いファイルは残さずに消し、`BACKUP_TOKEN` も入れ替える

## CouchDB の文書を確かめる

漏れていた間に更新された日次の文書を一覧にする。`updated_at` は UTC なので、日本時間から 9 時間引いた時刻で指定する。パスワードは画面に出さずに読み込む。

```sh
read -rs P
curl -s -u "<ユーザー名>:$P" -H 'Content-Type: application/json' \
  https://<CouchDB のホスト>/health/_find \
  -d '{"selector":{"updated_at":{"$gte":"<漏れた可能性のある最初の時刻（例: 2026-10-01T00:00:00Z）>"}},"fields":["_id","updated_at"],"limit":1000}'
unset P
```

- `health` は `COUCHDB_HEALTH_DB` の既定の名前。変えている場合はその名前にする
- Android アプリの自動送信は直近 7 日分を送り直すので、その範囲は正当な送信でも更新される。それより前の日付が、送った覚えの無い時刻に更新されていれば疑う
- 削除された文書は `updated_at` では見つからない。日数が減っていないかは、バックアップの `--dry-run` の表示と比べる（[backup.md](backup.md#1-中身を確かめる書き込まない)）
