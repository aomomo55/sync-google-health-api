# 0017: 設計の原則（DRY・KISS・YAGNI など）の線の引き方を決める

- ステータス: 採用
- 日付: 2026-10-07

## 背景

REVIEW.md の観点は、書き方の決まり（識別子・`const`）、依存の向き、このプロジェクト固有の前提が中心で、「コードが素直か」「同じ知識が何か所にも書かれていないか」を見る項目が無かった。

DRY・KISS・YAGNI などの原則は、名前を並べるだけでは使いにくい。原則どうしがぶつかることがあり（DRY を進めすぎると抽象化が増えて KISS に反する）、そのときにどちらを取るかで人やエージェントの判断がばらつく。

## 決定

原則と、このプロジェクトでの線の引き方を AGENTS.md の「変更するときの約束」に書き、REVIEW.md には「確認すること」として並べる。

- **DRY**: 規則・定数・形式など「同じ知識」の重複は、2 か所目でまとめる。処理の形が似ているだけの重複は、3 か所目でまとめるのを基本にする。見た目が似ていても変わる理由が違うコードは、重複とみなさない
- **KISS**: DRY とぶつかったら読みやすさを優先する。まとめた結果、呼び出し側で分岐や引数が増えるならまとめない。抽象化は、実装が 2 つ以上あるか、テストで差し替えるなどの理由があるときだけ作る
- **YAGNI**: 今の要件に無い機能・引数・設定項目・拡張点を「将来使うかも」で足さない
- **単一責任**: 1 つの関数・クラスに、変わる理由の違う複数のことをさせない（計算と I/O を混ぜない、など）
- **マジックナンバーの定数化**: 意味のある数値（日数、リトライの間隔や回数、上限など）は、名前を付けた定数にする
- サーバー（TypeScript）と Android（Kotlin）にまたがる同じ規則は、言語が違うので 1 か所にまとめられない。同じ規則であることをコメントで示し、同じ入力に対するテストを両方に置く

### 既存の重複: `mapLimit` と `writeMany`

並列数を絞って非同期の処理を回すコードが、`server/src/sync/note-sync.ts` の `mapLimit` と、`server/src/vault/vault-writer.ts` の `writeMany` の worker の 2 か所にある。これは **まとめず、このままにする**。

- 規則や形式のような「同じ知識」ではなく、処理の形が似ているだけの重複で、まだ 2 か所しかない
- `writeMany` の worker は、失敗を集めて続ける処理と進捗の通知も担っている。`mapLimit` に寄せると、`writeMany` 側でそれらを別に書くことになり、読みやすさがほとんど変わらない
- 3 か所目が出たら、`shared/concurrency.ts` に `mapLimit` を置いて寄せる（ADR 0016 の決まりに従い、そのときに `shared` の検査テストも足す）

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 原則と線の引き方を一緒に書く（採用） | ぶつかったときの判断がそろう | 線の引き方の数字（2 か所・3 か所）は目安で、例外の判断は残る |
| 原則の名前だけを並べる | 短い | 解釈が人によって違い、DRY の進めすぎなどを止められない |
| 書かない | 手間が無い | レビューで「素直さ」や「知識の重複」を見る観点が抜けたまま |

## 結果

- AGENTS.md の「変更するときの約束」に原則と線の引き方を、REVIEW.md に「設計の原則」の節を加えた
- 数字の目安は機械的には検査しない。レビューで判断する
