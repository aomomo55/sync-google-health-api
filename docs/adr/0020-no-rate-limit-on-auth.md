# 0020: 認証の試行回数を制限しない

- ステータス: 採用
- 日付: 2026-10-07

## 背景

サーバーはインターネットに公開していて、`/api/*` は `API_TOKEN`、`/backup/*` は `BACKUP_TOKEN` の Bearer 認証で守っている。認証に失敗したリクエストの回数を制限していないので、トークンを総当たりで試されたときに止める仕組みが無い（GitHub issue #50）。

前提となる事実は次のとおり。

- サーバーが受け付けるトークンは `API_TOKEN` と `BACKUP_TOKEN` の 2 つで、どちらも起動時に 32 文字以上、英数字と `. _ ~ + / -`（末尾の `=` は可）に限ると検査している（`server/src/config.ts`）。手順書では `crypto.randomBytes(32)` の 16 進表記（64 文字、256 ビット）で作るよう案内している
- 32 文字の 16 進でも 128 ビットあり、1 秒に 100 万回試しても、当てるまでの時間は宇宙の年齢を大きく超える。比較は `hono/bearer-auth` で行い、かかる時間から値を推測されることもない
- 利用者は 1 人で、マシンは 1 台。使われていないときは止まり（`auto_stop_machines`）、リクエストが来ると起動する
- `OBSIDIAN_MCP_TOKEN`（16 文字以上）は、このサーバーが obsidian-sync-mcp に送るもので、このサーバーでは受け付けない

## 決定

認証の試行回数の制限は、今は入れない。トークンの長さと文字の検査を起動時に行うことで、総当たりが成り立たないようにしておく。

次のときに見直す。

- 受け付けるトークンの最小の長さを短くする、または人が覚えるパスワードのような、推測できる値で認証する経路を足すとき
- 利用者が複数になる、マシンを複数台にするなど、前提が変わるとき
- 失敗したリクエストの量で、費用やほかの処理に影響が出たとき

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **制限しない** | 何も足さなくてよい。正しいトークンを持つ利用者が締め出されることが無い | 失敗したリクエストを大量に送られても止めない（総当たりは成り立たないので、問題になるのは負荷だけ） |
| Hono のミドルウェアで、メモリ上で回数を数えて制限する | アプリの中だけで完結する | マシンが止まるたびに数がリセットされる。複数台では台ごとに数える。送信元の IP で数えると、プロキシの後ろでの扱いや、利用者自身の締め出しを考える必要がある。トークンが十分に長いので、守れるものが増えない |
| fly.io やその前段のプロキシで制限する | アプリに手を入れずに済む | 設定や構成が増える。上と同じく、守れるものが増えない |

## 結果

- 認証まわりのコードと設定が増えない
- 安全性はトークンの長さと乱数の質に頼る。起動時の検査は長さと文字だけで、乱数で作ったかは確かめられないので、手順書どおりに作ることが前提になる
- 失敗したリクエストによる負荷は防がない。マシンが起動したままになるなど、気づいたら見直す
- トークンが漏れたときは、回数の制限では防げない。値を入れ替える（[rotate-secrets.md](../rotate-secrets.md)）
