# 0024: UX 観点のレビューの材料は docs/review/ に置き、REVIEW.md から参照する

- ステータス: 採用
- 日付: 2026-10-24

## 背景

PR #64（朝の睡眠の未反映を知らせる通知）のレビューで、「時間帯の設定によっては起きる前に通知が鳴る」という問題が見つかった。REVIEW.md はコードの差分を見る観点の一覧で、通知・画面・ノートを利用者の側から見て確かめる観点が無かった。

このアプリの利用者はほぼ本人 1 人で、毎日目にするのは画面より通知と Obsidian のノートである。送信の失敗や未反映に「アプリを開けば分かる」だけでは気づけない、という種類の問題は、コードの差分だけを見ても拾いにくい。

UX の観点を書こうとすると、各項目の確認の問いに加えて、「毎朝の流れ」「壊れたときの流れ」の説明が要り、REVIEW.md の他の節より長くなる。

## 決定

- UX 観点のレビューの材料（利用者の前提、毎朝の流れ、壊れたときの流れ、確認項目、文言の探し方）を `docs/review/ux.md` に置く
- REVIEW.md には「利用者の体験（UX）」の節を足し、通知・画面・ノート・エラー文を変える PR ではそこを見るよう、短い確認項目とリンクを書く
- `docs/review/ux.md` には「何を確かめるか」と「どこを見るか」だけを書き、今のコードの挙動や見つかった問題は書かない。問題は Issue にする
- 文言の一覧は写さず、探し方（`git grep`）だけを書く

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **docs/review/ に置き、REVIEW.md から参照する** | 流れの説明を長く書ける。REVIEW.md は確認項目の一覧のまま保てる。レビューの入口（REVIEW.md）から辿れる | ファイルが 1 つ増える。REVIEW.md だけ読んで ux.md を開かないと、見落とす |
| REVIEW.md に節を足すだけ | 入口が 1 つで済む | 流れの説明まで入れると、コードの差分を見る一覧が重くなる。PR ごとに全部を見ることになる |
| Claude Code のスキルにする | 必要なときだけ呼べる | 人がレビューするときに見えない。ほかのレビューの観点と置き場所が分かれる |
| 今の挙動と問題点も文書に書く | 1 か所で全部が分かる | 直すたびに文書が古くなる。コードの行番号もすぐずれる |

## 結果

- 通知・画面・ノートを変える PR で、UX の観点が REVIEW.md の流れの中で見られる
- 見つかった問題は Issue で追うので、`docs/review/ux.md` は直したあとも古くならない
- 流れや確認項目が変わったとき（新しい通知や画面を足したとき）は、`docs/review/ux.md` も更新する必要がある
- レビューで実際のノートを見ることはあるが、Issue や PR に実在の健康データの値は書かない（ルートの AGENTS.md の約束を守る）
