# 0016: 複数の層から使う汎用の部品は shared に置く

- ステータス: 採用
- 日付: 2026-10-06

## 背景

AGENTS.md で依存の向きを決め、同じ層どうしの横断を禁じた（`takeout` が `notes` を使う、など）。このとき、共通で必要なものは `domain` に置くとしていた。

しかし、複数の層から使いたいものには、健康データと関係の無い汎用の部品もある。たとえば、並列数を絞って非同期の処理を回す関数や、汎用の基底クラスなどである。こうしたものを `domain` に置くと、「日次・月次のデータ型と集計」という `domain` の意味がぼやける。一方で、各層に同じものを書けば重複になる。また、ある層の中に置いて別の層から import すれば、横断の禁止に反する。

## 決定

- 複数の層（Android では複数の機能）から使わざるを得ない、健康データを知らない汎用のものは `shared` に置く（server は `src/shared/`、Android は機能ごとにパッケージを分けたときの `shared` パッケージ）
- 健康データの型や規則など、このアプリの知識を含むものは、これまでどおり `domain` に置く
- `shared` は他のどの層にも依存しない。どの層からも `shared` を使ってよい
- 1 つの層でしか使わないものは、その層の中に置く。2 つ目の層で必要になった時点で `shared` に移す
- ディレクトリは、最初に置くものができたときに作る

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| `shared` を作る（採用） | `domain` の意味を保てる。依存の向きが単純（`shared` は何にも依存しない） | 何でも置ける場所になりやすい。「複数の層から使う」「健康データを知らない」の 2 条件をレビューで確かめる必要がある |
| `domain` に置く（これまで） | 層が増えない | 健康データと関係の無いものが `domain` に混ざる |
| 使う層ごとに複製する | 層の独立性が高い | 同じ処理の修正漏れが起きる |

## 結果

- REVIEW.md に、`shared` に置いたものが 2 条件を満たすか、`shared` から他の層を import していないかの確認項目を加えた
- 何でも `shared` に入れる「置き場」にならないよう、先回りして移さないことを AGENTS.md に書いた

## 追記（2026-10-07）: 何でも入れる場所にしないための決まり

`shared` を許すと、`utils.ts` のような曖昧な名前のファイルに何でも入れる場所になりやすい。そこで、上の決定に次の決まりを加えた（#36）。

- 中身を表す名前にする。`utils` / `helpers` / `common` / `misc` / `lib` のような名前のファイルやフォルダは作らない（例: `shared/concurrency.ts` に `mapLimit`）。名詞 1 つで名前を付けられないものは、`shared` に向いていない合図とする
- 1 ファイル 1 テーマにする。テーマが違うものは別のファイルにする。`shared/index.ts` のような再エクスポートだけのファイル（バレル）は、どこで何を使っているかが見えにくくなり、とりあえず足す先になりやすいので作らない
- 置く条件（複数の層から使う・健康データを知らない）に加えて、外す条件を決める。使う層が 1 つに減ったら、その層へ戻す
- 禁止した名前のファイルが無いことと、`shared` から他の層を import していないことを、vitest のテスト 1 本で確かめる。今は `shared` が無く、先に作ると YAGNI に反するので、`shared` を初めて作るときにこのテストも足す
